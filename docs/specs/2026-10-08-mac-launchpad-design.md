# MacLaunchpad 设计规格

日期：2026-10-08

MacLaunchpad 是一个 macOS 程序坞应用。点开后进入全屏网格，展示本机已安装的 App，点击图标打开。技术是原生 SwiftUI。第一版包含搜索、分页、文件夹和拖拽排序。没有全局快捷键，没有菜单栏图标。

程序坞上的显示名是「程序启动台」，避免和系统启动台重名。布局文件目录名使用 `MacLaunchpad`。

## 已确认的范围

第一版要做：

- 扫描已安装 App，全屏网格展示，点击打开
- 键盘输入即时搜索
- 多页，每页 7 列 × 5 行
- 文件夹
- 拖拽排序，并记住位置
- 从程序坞点图标打开

第一版不做：

- 全局快捷键
- 菜单栏图标
- 扫描结果磁盘缓存
- 文件夹套文件夹
- 界面自动化测试

## 界面行为

窗口在打开它的那块屏幕上进入全屏。背景使用当前桌面壁纸并模糊。读不到壁纸时，用深色半透明底。

每页最多 35 个格子，从左到右、从上到下排列。底部圆点表示页码，点圆点可以翻页。触控板左右滑动，或左右方向键，也可以翻页。

图标使用该 App 自己的图标，名字使用显示名。图标取失败时，格子仍显示名字，并且仍然可以点击打开。

### 打开 App

点击图标后，用该 App 的路径打开它。打开成功后退出全屏并隐藏窗口，进程留在程序坞。再次点击程序坞图标时，窗口重新出现并进入全屏。

打开失败时留在当前画面，搜索框下方显示「无法打开〔名称〕」，约 2 秒后消失。

在主网格按 Esc，效果和打开成功相同：退出全屏并隐藏窗口，不退出进程。Cmd-Q 退出进程。

### 搜索

顶部有搜索框。直接打字，或点搜索框，都进入搜索。搜索只改变当前画面，不修改已保存的布局，搜索状态下不能拖拽。

匹配规则是显示名的子串，忽略大小写。文件夹里的 App 也参与匹配。结果是一页平铺的 App，不显示文件夹格子。

Esc，或把搜索文字清空，回到进入搜索之前的那一页。搜索时方向键不翻页，字符进入搜索文字。正在编辑文件夹名称时，键盘输入不进入搜索。

### 文件夹

把一个 App 拖到另一个 App 上松开，在目标 App 原来的位置生成文件夹。文件夹里的顺序是目标 App 在前，被拖动的 App 在后。默认名称是「文件夹」。

把一个 App 拖到已有文件夹上松开，这个 App 追加到该文件夹末尾。

文件夹不能包含文件夹。把文件夹拖到 App 或其他文件夹上，只当作普通换位，不产生嵌套。

点击文件夹进入内页。内页是 7 列的网格，行数随成员增加，第一版不做文件夹内分页。文件夹标题可以编辑。提交空名称时恢复为「文件夹」。按 Esc 或点击内页以外的区域，回到主网格。

在内页把 App 拖出网格，放到变暗的背景上，该 App 离开文件夹，回到这个文件夹所在页的末尾。该页已满时，放到之后第一页的末尾；后面没有空位就新建一页。

文件夹内可以拖拽改变成员顺序。

### 拖拽排序

在主网格拖拽会改变顺序，松手后立刻保存。同一页内换位。拖到屏幕左缘或右缘并停留约 400 毫秒，翻到相邻页，然后可以放下。

已经在最后一页时，停在右缘约 400 毫秒会新建一页并翻过去。停在第一页的左缘不产生动作。

每个 App 或文件夹只属于一页。从一页拖到另一页后，它离开原来的页，后面的格子向前补齐。

## 模块

五个单元。布局和合并逻辑不依赖 AppKit，可以用单元测试覆盖。扫描要读真实目录。打开 App 只是对系统接口的薄封装。

### AppCatalog

职责：从磁盘找出要展示的 App。

输入：一组扫描根目录。

输出：`AppRecord` 列表。每条包含 `bundleID`、`displayName`、`url`。

规则：

- 扫描这些位置（目录不存在就跳过）：
  - `/Applications`
  - `~/Applications`
  - `/System/Applications`
  - `/Applications/Utilities`
  - `/System/Applications/Utilities`
  - `/opt/homebrew/Caskroom`
  - `/usr/local/Caskroom`
- `/Applications`、`~/Applications`、`/System/Applications` 和两个 Utilities 目录只看直接子级的 `.app`。
- Caskroom 只看「配方名 / 版本号 / 直接子级 .app」。
- 不进入任何 `.app` 的内部。
- 读不到 bundle、没有 bundle id，或显示名和文件名都空的，跳过这一条，继续扫描。
- 显示名依次取 `CFBundleDisplayName`、`CFBundleName`、去掉 `.app` 的文件名。
- 同一个 `bundleID` 只留一条。优先级从高到低：
  1. `~/Applications`
  2. `/Applications`
  3. `/opt/homebrew/Caskroom`
  4. `/usr/local/Caskroom`
  5. `/System/Applications` 与 `/System/Applications/Utilities`
  6. `/Applications/Utilities`

### LayoutStore

职责：读写布局文件。

路径：`~/Library/Application Support/MacLaunchpad/layout.json`

文件只保存 bundle id、页、格子顺序、文件夹 id、文件夹名称和成员。不保存图标，不保存路径。

页面上的一项是 App，或文件夹。文件夹成员只是 bundle id 列表。

读文件时做校验。文件不存在、不是合法 JSON、或结构不符合上面的形状，就视为没有布局。调用方负责生成新布局。`LayoutStore` 不扫描磁盘上的 App。

写入失败时向调用方返回失败。不抛到界面崩溃，不回滚内存里的布局。

### LaunchpadSession

职责：把这次扫描结果放进已保存的布局。

输入：`AppRecord` 列表，以及 `LayoutStore` 读到的布局或空。

输出：当前页列表。每一项都能对应到一条仍存在的 `AppRecord`。

规则：

- 没有可用布局时，按显示名做本地化、不区分大小写的排序，每 35 个一页。
- 有布局时，按保存的页和顺序放回仍存在的 App。
- 已卸载的 App 从页面和文件夹成员里删除。删除后，同一页里后面的项目向前补齐，不留空格。
- 成员变空的文件夹删除，并按同样的规则补齐那一页。
- 末尾的空页删除。中间的空页也删除，后面的页依次前移。
- 扫描里多出来的 App，追加到第一张还有空位的页的末尾。都满了就新建一页。
- 搜索、当前页码、文件夹是否打开、短暂的错误提示，都是界面状态，不写入布局。

拖拽、新建文件夹、改名产生新布局后，先更新内存，再调用 `LayoutStore` 写入。写入失败时保留这份内存布局，下一次布局变化再次写入。

### LaunchpadView

职责：全屏网格、搜索、翻页、文件夹内页和拖拽手势。

它读取 `LaunchpadSession` 的当前布局，把用户操作交回 session。它不自己决定扫描目录，也不自己拼接 JSON。

### AppOpener

职责：按 `AppRecord.url` 打开 App。

成功返回成功。失败返回失败，由界面显示短暂提示并保持当前画面。

## 数据流

1. 应用启动，窗口进入全屏。
2. `AppCatalog` 扫描。
3. `LayoutStore` 读取 `layout.json`。
4. `LaunchpadSession` 合并出当前页。
5. `LaunchpadView` 显示网格。
6. 排序、文件夹和改名更新 session，并写入 `layout.json`。
7. 点击 App 时，`AppOpener` 打开它。成功则隐藏窗口。

每次打开窗口都重新扫描。第一版不把扫描结果写到磁盘。

## 出错

| 情况 | 行为 |
| --- | --- |
| 某个扫描根目录不存在 | 跳过 |
| 某个包读不了或没有 bundle id | 跳过，继续扫描 |
| 图标取失败 | 显示名字，仍可打开 |
| 壁纸读失败 | 深色半透明底 |
| `layout.json` 缺失或损坏 | 按当次扫描重建布局，程序不崩溃 |
| 写入 `layout.json` 失败 | 画面保持当前布局，下次变更再写 |
| 打开 App 失败 | 留在当前画面，短暂提示「无法打开〔名称〕」 |

## 测试

使用 XCTest，只测纯逻辑。第一版不写界面自动化测试。

- 去重：同一个 bundle id 出现在用户目录、`/Applications`、Caskroom 和系统目录时，保留用户目录那一份。只出现在系统目录和 Caskroom 时，保留 Caskroom 那一份。
- 新 App 追加到第一张未满的页。全部已满时新建一页。
- 卸载后的 App 从页面和文件夹删除。空文件夹删除。空页删除，后面的页前移。
- 损坏的 `layout.json` 被忽略，结果等于按显示名排序后的新布局。
- 拖到另一个 App 上生成文件夹，位置在目标 App 处，成员顺序是目标在前。
- App 从一页移到另一页后，只出现在新页，原页后面的项目补齐。

`AppOpener` 不在单元测试里调用真实的打开动作。
